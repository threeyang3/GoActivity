# 日常无人值守运行

2026-10-12 的检查表明：本地服务和定时任务正在运行，但微信仍有限频，
当前文章数据主要来自历史采集，飞书对账也存在差异。HTTP 正常不等于数据管道正常。

## 自动处理的故障

- 桌面管理器对服务启动失败、退出、连续健康检查失败进行重试，最长间隔 5 分钟。
  持续健康 5 分钟后清零重试计数；手动停止会取消重试，避免后台自行重新启动。
- 停止不健康的服务时终止整个进程树，避免遗留 Python、浏览器或机器人子进程。
  Windows Job Object 也会在管理器异常退出时清理其子进程，让计划任务能干净重启整个服务树。
- 机器人断线同样采用 5/10/20/40/80/160/300 秒退避，继续等待恢复。
- Windows 当前用户的 `GoActivity Desktop Recovery` 计划任务在登录时启动轻量守护进程，
  守护进程直接监测桌面程序退出，失败后按 5 秒到 5 分钟退避重启；手动正常退出不重启。
  任务自身配置的失败重试作为补充，不能只凭该配置认定异常退出必然恢复。
  登录注册表入口也启动同一任务，防止不同入口竞争后脱离任务监督。
  电脑须开机且用户已登录；睡眠、关机、退出登录期间不能持续采集。
- 定时任务允许 1 小时内的执行延迟，并合并错过的重复触发，避免唤醒后的请求风暴。
  数字 cron 星期按 Unix 规则解释：1 为周一，0/7 为周日。更长停机不承诺补发报告。
- 微信限频保留持久化冷却，自动续期按实际续期结果计数，且禁止续期任务重叠。
  本地会话状态同样检查动态到期时间。日志和授权成功通知不输出 Token。

## 备份与状态

桌面程序启动时、此后每 6 小时，调用项目 Python 对两个 SQLite 数据库执行在线备份。
备份包含已提交的 WAL 内容，并执行 `PRAGMA quick_check`；每个数据库保留最近 28 个快照
（按正常 6 小时间隔约 7 天）。失败每 5 分钟重试，旧的可用快照继续保留。

备份位于配置的 `STORAGE_DIR/backups`。默认 `storage/backups/status.json` 记录最近结果。
`GET /automation/status` 返回备份、调度、采集状态；超过 7 小时的备份标为 stale。
快照只包含数据库，不包含文章图片、Markdown、`.env`、微信 cookie 文件和飞书 CLI 配置。
它们是本机恢复点，无法防止整块磁盘损坏；不要将包含账户数据的快照公开提交。
恢复数据库前先停止两个服务并保留当前库，使用 SQLite backup API 从快照还原，
避免在仍有连接或旧 WAL 文件时直接替换主数据库文件。

`GET /health` 的采集检查区分服务可达和实际采集成功，返回授权到期、冷却以及最近成功时间。
只有近期成功读取过对应公众号，且文章本身较旧，才将其视为正常停更来源。
所有采集请求被跳过时标为受阻，不再报告“采集完成”。

## 仍需人工处理的边界

微信强制扫码、账号风控或长期接口限频不能由本地软件可靠消除。
飞书权限撤销、服务商凭证失效、余额不足也需账户所有者处理。
告警沿用配置的飞书接收人和冷却规则；告警渠道自身不可用时仍需查看本地状态。
对账仍是只读检测；当前高缺失比例不会自动重建记录或覆盖用户在飞书的修改。

建议平时查看控制中心状态；只有告警、授权要求或明显数据延迟时介入。
这些机制减少日常维护，不能作为已经经过长期运行验证的稳定性保证。
